# URL HTML 邮箱导入设计

## 目标

让桌面端和 Python 注册流程接受以下邮箱导入格式：

```text
邮箱地址----http://或https://开头的邮件页面URL
```

该 URL 可以来自任意网站，页面也不要求使用固定的 HTML 标签、类名或邮件服务商模板。选择这种邮箱后，注册流程继续使用现有的“仅注册、不接手机号”模式，并从页面中轮询 OpenAI/ChatGPT 邮件验证码。

## 范围与边界

- 支持每行一个 `邮箱----URL` 记录。
- 只接受 `http://` 和 `https://` URL；不接受其他协议。
- 按用户要求，不限制域名、IP 地址或内网地址，也不增加 SSRF 拦截。
- 每次轮询只请求导入的 URL。不会点击、抓取或跟随页面正文中的“全部邮件”等链接。
- HTTP 客户端可以正常跟随服务器重定向。
- 不实现需要浏览器执行 JavaScript、登录交互、Cookie 注入或验证码破解的网站。首版解析服务器直接返回的 HTML。
- 不改变现有 Chatai、Graph、Gmail、ReMail、CF Worker 等邮箱格式和行为。

## 导入与账户模型

### 桌面端

桌面端导入器按最多一次分隔解析 `----`。当左侧是合法邮箱、右侧是合法 HTTP(S) URL 时，将该行识别为“URL 邮箱”，而不是现有四字段 Chatai 邮箱。

邮箱池列表应显示该账户及其 URL 邮箱类型。选中它启动注册时，桌面端创建临时邮箱文件并传给 Python 注册命令；现有 `--registration-at-only` 和 `--no-phone-reuse` 参数保持不变。

### Python

`MailboxAccount` 增加专用的 `inbox_url` 字段，并使用 `url_html` provider。URL 不复用密码、刷新令牌或其他凭据字段，避免后续代码误判认证方式。

解析规则按明确格式优先：

1. 已有带前缀的 provider 格式保持原顺序。
2. 两字段 `邮箱----HTTP(S) URL` 解析为 `url_html`。
3. 四字段 `邮箱----密码----客户端ID----刷新令牌` 仍解析为 Chatai。
4. 其他字段数量或非 HTTP(S) 的两字段记录保持无效，不静默猜测。

## HTML 提取架构

新增独立的 URL HTML 邮箱适配器。它只负责下载和标准化页面，不负责最终判定验证码。这样现有 OTP 过滤、时间检查、排除码和轮询逻辑可以继续复用。

适配器按两级策略生成标准邮件候选：

### 1. 语义容器提取

优先把常见的独立内容块视为邮件候选，例如 `article`、`details`、表格行、列表项，以及具有邮件语义的卡片或消息容器。每个候选通过标签语义和可见文本推断：

- 主题：`subject` 类/属性、`summary`、标题标签或候选首行；没有明确主题时，从候选中选取包含 OpenAI/ChatGPT 与验证码语义的短文本作为主题提示，而不是使用无关的页面标题。
- 发件人：包含 sender/from/发件人 等标签的字段。
- 收件人：包含 recipient/to/收件人 等标签的字段。
- 时间：`time` 标签、日期属性或正文中的常见日期时间格式。
- 正文：候选容器的可见文本，排除脚本、样式和导航噪声。

类名只是提示，不是硬编码的网站条件。没有某个字段时仍可产生候选，由后续 OTP 规则决定是否可用。

### 2. 整页可见文本兜底

页面没有可识别的独立邮件容器时，将标题、主要标题和整页可见文本组成一个候选。兜底候选仍必须通过现有 OpenAI/ChatGPT 主题与验证码上下文规则，不能因为页面存在任意六位数字就直接返回。

适配器输出与其他邮箱 provider 一致的标准消息字典，包括稳定的内容哈希 ID、主题、正文、可选时间、发件人和收件人。URL HTML provider 接入并扩展现有的发送前快照入口：发送验证码前记录当前候选 ID，轮询时忽略该基线候选，借此排除旧页面内容。

## 验证码选择与防误取

URL HTML provider 复用现有邮件 OTP 筛选入口，并保留这些条件：

- 优先匹配 OpenAI/ChatGPT 的验证码、verification code 或 login code 语义。
- 如果页面提供主题、发件人、收件人或时间，使用现有配置进行筛选。
- 有可靠时间时拒绝早于本次验证码请求的邮件。
- 没有可靠时间时，使用请求验证码前采集的候选 ID 快照排除旧内容；只接受轮询后新出现或内容发生变化的候选。
- 继续尊重本次流程传入的排除验证码，防止重复使用刚刚消费过的验证码。

这意味着首次打开页面时已经存在的旧验证码不会在后续轮询中被误用。

## 网络、日志与失败行为

- 使用现有邮箱网络配置；配置邮箱代理时优先使用它，保持与其他邮箱 provider 一致。
- 设置有限的连接/读取超时，并限制 HTML 响应体大小，避免注册线程无限等待或下载异常大文件。首版上限为 2 MiB。
- 非成功 HTTP 状态、非 HTML/文本响应、超限响应、解码失败和无候选结果都返回清晰错误，由现有轮询逻辑重试或超时退出。
- URL 可能在路径、查询参数或用户信息中包含访问凭据。日志和界面错误不得输出完整 URL，只显示协议、主机和经过隐藏的路径摘要。
- 由于用户明确选择信任导入 URL，系统不做域名、DNS、私网 IP 或重定向目标限制。

## 测试策略

### Python 单元测试

- 两字段 HTTP 和 HTTPS 格式成功解析为 `url_html`。
- 四字段 Chatai 及其他已有格式保持原行为。
- 非 HTTP(S)、缺少邮箱、缺少 URL 和多余字段被拒绝。
- 覆盖用户示例结构的静态 HTML 能提取主题、时间、发件人和六位验证码。
- 使用完全不同标签与类名的 HTML 仍能通过语义/整页兜底提取。
- 多封邮件页面选择符合时间和 OpenAI/ChatGPT 语义的新验证码。
- 普通订单号、旧验证码、脚本中的数字和导航文本不被误取。
- HTTP 错误、超时、超限和非 HTML 响应产生可诊断错误，且错误不泄露完整 URL。

### 桌面端测试

- 导入器接受两字段 URL 邮箱并在邮箱池中正确分类。
- 选中 URL 邮箱时生成正确临时文件和 Python 邮箱参数。
- 现有四字段 Chatai 与三字段 Graph 分类不回归。
- 注册命令仍包含 `--registration-at-only` 和 `--no-phone-reuse`。

### 验证

依次运行相关 Python 测试、完整 Python 测试、桌面端测试和正式桌面编译。最后使用本地静态测试服务器验证轮询行为，不在自动化测试中访问用户提供的真实 URL。

## 完成标准

- 用户可导入 `邮箱----任意HTTP(S)页面URL` 并在桌面端选中注册。
- 至少两种结构明显不同的静态 HTML 页面能够正确提取验证码。
- 旧验证码与无关六位数字不会被返回。
- 网络和解析错误可理解，且日志不泄露完整 URL。
- 所有既有邮箱格式测试、注册测试及桌面编译通过。
